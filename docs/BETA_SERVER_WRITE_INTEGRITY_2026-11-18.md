# PaperSignal beta: server-owned analysis writes (2026-11-18)

## Risk discovered in read-only production inspection

This is a **release-gated integrity fix**, not an analysis-engine change.

Before this fix, the Supabase Data API grants allow the `authenticated` role to:
- INSERT arbitrary rows into `public.analyses` (including the JSON result and model name).
- INSERT queued rows directly into `public.analysis_jobs`, bypassing the application API's checks and potentially consuming Worker/LLM resources.
- UPDATE selected analysis job state columns and paper status/page-count fields.

Current RLS correctly restricts each user to their own data, as demonstrated by a read-only two-owner, actual-row policy simulation on 2026-11-18. **Owner isolation does not by itself protect the integrity of results and worker scheduling.**

## Code and migration prepared (not deployed)

1. The API verifies the caller's Supabase JWT and paper ownership using the caller's token as before.
2. Only the trusted API submits the job INSERT, using the existing `SUPABASE_SERVICE_ROLE_KEY` server-side. The frontend never receives this key.
3. The Worker already uses service_role and continues saving analysis results and job/paper statuses.
4. A new migration, generated by `supabase migration new beta_server_owned_result_writes`, removes client INSERT on `analyses` and `analysis_jobs`, client UPDATE grants on job status and paper status, and narrows `papers` INSERT to the upload fields only.
5. The live E2E synthetic upload fixture now uses only the allowed paper INSERT columns.

Existing Railway variable **names** were inspected: both `papersignal-api` and `papersignal-worker` have `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` configured. No secret values were retrieved or exposed.

## Test evidence

- Isolated Vercel Sandbox, Python 3.12 and the repo-pinned `backend/requirements-dev.txt`: `PYTHONPATH=/vercel:/vercel/backend python -m pytest -q` → **103 passed, 1 skipped**. The skipped case is the intentionally opt-in live E2E; it was **not** run.
- New tests assert that authenticated paper lookup stays scoped to the user's JWT, queue INSERT uses server-side `sb_secret_*` credentials without a bearer JWT, and a missing server secret fails closed with HTTP 503.
- PostgreSQL grammar check of the migration with `pglast` → **10 SQL statements parsed successfully**. This is syntax validation, not a migration execution or transactional integration test.
- The previous real DB read-only role tests confirmed: a selected owner can read their own paper and existing analysis, while the second owner cannot read the target paper, analysis, job or Storage metadata.
- Frontend tests: 75/75; isolated browser anonymous and synthetic UI tests: 15/15 in the earlier QA milestone. Neither proves new production server authorization.

## Safe deployment order — requires independent approval

**Do NOT run this migration before the server API change is deployed and verified.** Existing live API code enqueues using the client JWT; applying REVOKE first would break legitimate analysis starts.

1. Review this branch and all parent Draft PR changes. Verify that the API and Worker both have their existing service key available (the names are configured).
2. Deploy the updated API (not the Worker/engine) using the normal reviewed Railway release path, while the old DB grants remain. Confirm `/health`, valid owned-paper enqueue and unauthorized paper rejection with disposable, non-sensitive QA data.
3. Only once the server-side insert is confirmed in the live environment, apply the reviewed migration to the existing Supabase project. Verify the assertions in `supabase/tests/beta_write_grants.sql` and re-run Supabase security advisors.
4. Repeat the existing live two-user E2E, including PDF upload (with only allowed columns), analysis completion and denial of access to the other user's paper and PDF. Check API/Worker runtime logs for errors.
5. Test real email/Google login, signed original PDF and citation navigation in browser before declaring beta ready.

No new Supabase project or API key is needed. No production database migration, API deploy, Worker deploy, rollback or promotion happened while preparing this branch.

## Rollback and incident response

- If API release fails **before** the DB migration, roll back the API to its previous known-good deployment; the database is still unchanged.
- After client-grant REVOKEs, rolling back the API to an older version that inserts jobs with a user JWT is **not compatible**. Prefer restoring the reviewed API with the service-role write path rather than reopening client INSERT.
- Restoring client write grants/policies would revive the identified integrity and spending risk; it must be treated as an explicitly reviewed last-resort emergency change, not an automatic rollback.
- Do not merge to `main` until deployment sequencing and tests are signed off.

`20261112155952_initial_paper_analysis_schema` and
`20261112160036_authenticated_analysis_writes`, whereas repository
baseline migration filenames begin with `20261113000000_initial_schema.sql`
and `20261113010000_analysis_jobs.sql`. These are different migration
history entries even though the schema is already present.

**Do not run `supabase db push` blindly from this branch.** It may try to
reapply earlier schema migrations. First reconcile the repository migration
history with the live project's `list_migrations`, or apply only this
reviewed new migration through an explicitly authorized migration mechanism
that records its real version exactly once.

At the time of inspection, the new migration version
`20261117215315_beta_server_owned_result_writes` is **not in the live
migration list**, and the corresponding client write grants remain active.
